# H616 VE: why 10-bit 4K with P010 output is slow, and what is achievable (web + static research)

Date: 2026-11-02. Scope: research only. No board access, no external code run, no binaries executed.
Downloads: `harness/research/vdec-web/dl/` (untrusted data, `SHA256SUMS` one level up). Static disassembly used `aarch64-linux-gnu-objdump` on the T527 CedarC libs already in `ve-encoder/dl/orangepi-build/x/`.
Tags: **[M]** measured (by whom), **[C]** claimed by a source without data, **[I]** my inference, **[S]** read from source/disassembly.

## 0. Bottom line

1. **The P010 path does not use the fast tiled primary output. It writes a *linear* NV12 reconstruction and then adds the P010 secondary write on top.** [S] In our tree (Jernej's patch 11 `bfad2e9a00d2`, plus `cedrus.h:cedrus_dst_frame_fmt()`), the hidden reconstruction/reference surface is `V4L2_PIX_FMT_NV12` with a 64-byte stride. `cedrus_dst_format_set()` programs it as `VE_PRIMARY_OUT_FMT_NV12` (0x4<<4, linear). `cedrus_dst_p010_output_set()` then writes `VE_PRIMARY_OUT_FMT = NV12 | SECONDARY_EXT_NV12` (`cedrus_h265.c:826-837`, `cedrus_vp9.c:915-918`). The decoder therefore runs the *same* linear-primary mode that costs 8-bit HEVC 81.8 → 34.9 fps, plus the 2-bit plane, plus the P010 write. impl-vdec §9.1 says "8-bit tiled + 2-bit planes", which does not match the code.
2. **The linear penalty comes from the access pattern, not the number of bytes written.** [I] Tiled and linear NV12 write the same 12.4 MB per 4K frame. The +16.4 ms/frame for linear therefore cannot be a write-bandwidth limit of "0.75 GB/s". It has to be the inefficiency of linear-layout reconstruction writes and motion-compensation reference reads. The most likely mechanisms are DRAM page/bank misses and IOMMU micro-TLB thrash. A 3840-byte linear stride puts each luma row on its own 4 KiB page. A ~70-row MC fetch then touches more pages than the 64-entry per-master micro TLB holds (UM §3.12.2: micro TLB 64 words per master, macro TLB 4K words shared, PTW cache 512). A 32x32 tile is 1 KiB contiguous. The same pattern appears in H.264 (42 tiled vs 28.6 linear).
3. **The secondary (P010) write is the smaller part.** [I from our numbers] HEVC: 8-bit linear 28.7 ms/frame → Main10 P010 40.8 ms, so the 2-bit plane plus the secondary P010 costs about 12 ms. VP9: 8-bit tiled 13.1 ms → P2 P010 28.1 ms (no 8-bit linear VP9 number, so the split there is unknown).
4. **AFBC is the vendor's production path and has the only published 4K60 number on H616.** [C, developer measurement] Jernej Škrabec, LibreELEC commit 44fab077a4 (2026-10-31): "On H616, 4K60 decodes at 63 to 84 fps with AFBC, and at 18 (10-bit) to 47 fps (8-bit) with linear output." [S] For H616 (decoder IP 0x33010), the vendor library enables AFBC for VP9, H.264, H.265 and AVS2. In `ENABLE_AFBC_JUST_BIG_SIZE` mode it forces it at ≥3840x2160 (§3).

## 2. Best-evidenced explanation of the P010 slowdown

Facts (all [S] from our tree unless noted):
- 8-bit capture `NV12_32L32` → `VE_PRIMARY_OUT_FMT_TILED_32_NV12`; 8-bit `NV12` → `VE_PRIMARY_OUT_FMT_NV12` (linear). Both write 12.4 MB/frame. Measured 81.8 vs 34.9 fps.
- P010 capture: hidden recon = linear NV12 (stride `ALIGN(width, 64)`), plus the appended 2-bit plane via `VE_DEC_H265_OFFSET_ADDR_FIRST_OUT`, plus the secondary engine writing P010 (`VE_DEC_H265_CTRL_ROTATE_SCALE_OUT_EN`, `VE_DEC_SECOND_OUT_*`). The references the VE reads are the linear NV12 + 2-bit planes.
- The vendor H6 library, when *not* using AFBC, also uses a linear primary (YV12 by default; `h265.c` priPixelFormatReg 3) and appends the 2-bit plane after `w*h*3/2` (`vdecoder/fbm.c` l.254-270, Allwinner-Homlet H6-CedarC, LGPL). Allwinner never relied on a linear-primary 10-bit path for 4K60: on H6 the 4K H.265 route was AFBC (`controlEnableAfbc`, `ENABLE_AFBC_JUST_BIG_SIZE`).
- With AFBC, the vendor H6 code stops writing a chroma address into the reference frame-info (`h265_register.c` l.1254: chroma address set only if `bEnableAfbcFlag == 0`). **The VE then reads its references in AFBC form**, so both the writes and the MC reads are compressed. AFBC therefore saves bandwidth on both sides, not only at display time.

Inference [I]:
- The linear-primary penalty (+16.4 ms at 8-bit) is the dominant term in P010, and the secondary P010 write plus 2-bit overhead (~12 ms) is the smaller term. The "secondary engine write-bound at 0.75–0.9 GB/s" hypothesis is not supported: the 0.75–0.9 GB/s figure divided write bytes by extra time, while tiled mode writes the same bytes much faster.
- Candidate mechanisms for the linear penalty, in order of plausibility: (a) IOMMU micro-TLB misses (64 entries × 4 KiB = 256 KiB reach per master; one linear 4K luma row = 3840 B ≈ one page, so every MC block fetch or CTB write walks ~64+ pages). The TLB prefetch is already enabled for masters 0–5 in mainline (`sun50i-iommu.c` `sun50i_h6_variant.tlb_prefetch`), but prefetch predicts sequential access, not 2-D strided access. (b) DRAM row/bank misses on strided 2-D access. (c) Linear output engine internals (unknown).
- Predicted gains, untested: P010 with a *tiled* primary should save most of the 16 ms, giving ≈ 24 ms/frame ≈ 40 fps, still below 60. AFBC10 should reach ~60 (Jernej's 63 fps lower bound plausibly being 10-bit).

## 3. What the vendor stack does on H616 (libcedarc)

[S] T527 CedarC "stable_v1.3.0" glibc libs (`ve-encoder/dl/orangepi-build/x/t527_packages_jammy_libcedarc…/usr/lib/aarch64-linux-gnu/`), disassembled statically:
- `libvideoengine.so` `SetAfbcParam` (VDecoderRegister+0x408…0x650): for `ndecIpVersion == 0x33010` (H616 decoder IP, matching our board read 0x00033010), AFBC is marked capable for codec formats 0x113 VP9, 0x115 H.264, 0x116 H.265 and 0x118 AVS2. These values come from the `libvdecoder.so` DWARF enum (VIDEO_CODEC_FORMAT_VP9=275, H264=277, H265=278, AVS2=280). If `eCtlAfbcMode == ENABLE_AFBC_ALL_SIZE` (2), or `== ENABLE_AFBC_JUST_BIG_SIZE` (1) with width > 3839 and height > 2159, the library sets `eOutputPixelFormat = 4` (YV12, the AFBC carrier). For H6 (0x31010) only H.265 gets AFBC, and for 0x30210 only H.264/H.265 above 1920x1088. **So the vendor's 4K route on H616 is AFBC for all spec codecs.**
- `libvdecoder.so` also has `CDC_SINK_PIC_FORMAT_P010` (=4), `PIXEL_FORMAT_P010_UV/VU` (22/23), `bSecOutputEn`, `eSecOutputPixelFormat`, so P010 exists as a sink/secondary format. No evidence was found that it is used for 4K playback.
- Vendor H6 code (LGPL source) uses AFBC primary together with a linear secondary for ≥5K streams (`vdecoder.c` l.445: `bSecOutputEn=1, bScaleDownEn=1` while the AFBC disable is commented out; `h265_ref.c` second FBM `bAfbcModeFlag=0`). **AFBC primary + linear secondary is therefore a combination the vendor uses** (as a half-size display copy).
- Register names: VE top `0xEC VECORE_PRIMARY_OUT_FORMAT_REG` {`primary_output_format` [6:4]: 0 32x32 tile, 1 **128x32 tile ("buffer should be 4K aligned")**, 2 YU12, 3 YV12, 4 NV12, 5 NV21; `second_special_output_format` [2:0]}. `0xE8 CHROMA_BUF_LEN0` {`output_data_format` [31:30], `sdrt_chroma_buf_len`}. `0xC4/0xC8/0xCC` pri chroma len / pri stride / sec stride. H.265 `+0x8C HEVC_10BIT_CONFIGURE` (A133 DWARF): `lower_2bit_data_stride_first_output`:11, `…_second_output`:11, `lower_2bit_data_output_enable`:1 (bit 22), `second_out_format`:2 (bits 23-24; mainline names 1 = P010, 2 = 10BIT_4x4_TILED). VP9 `+0x8C` (T527 DWARF): `first_output_lower_2bit_stride`:12, `snd_low2_out_enable_or_P010_for_sec`:1 (bit 12), `snd_with_high10b`:1 (bit 13). VE_MODE AFBC bits: `compress_en` 29, `min_val_wrap_en` 27, `rgb_def_color_en` 26, `bodybuf_1024_aligned` 12, compress mode [4].
- **VE DRAM traffic counters exist**: VE top `0x20 dram_read_cntr` and `0x24 dram_write_cntr` {counter:31, enable:31}, with `VE_MODE` bits 8/9 `read_counter_sel` / `write_counter_sel`. Also `0x10 mmc_req_wnum` and `0x14 cache_req_wnum` (24-bit). Source: `libawvp9HwAL.pahole.txt` VETOP_REGISTER_LIST and H6-CedarC `ve/include/veAwTopRegDef.h`. Units and select semantics are undocumented.

## 5. AFBC10 → DE33: status and what is needed to test it

Is it proven at 4K60? **Partly.** The decode side is claimed by a developer measurement (63–84 fps, §1). Scanout is implemented and merged into LibreELEC master (2026-11-01), but nobody has published a "4K60 10-bit HEVC plays without drops on H616" report. No user report for Kodi on LibreELEC/H6 playing 4K60 10-bit was found either. LE commit 77c51768df (2026-11-01) fixed "don't wait an extra vblank for DE3 scanout, which halved the frame rate of 60 fps video on H6", which implies that **60 fps playback on H6 was broken until 2026-11-01**.

Pieces (all Jernej Škrabec unless noted):
- **Kernel, VE side:** LibreELEC `projects/Allwinner/patches/linux/` 0406–0444. Key ones: 0411 VP9, 0412–0414 P010, 0416 AFBC fourccs, 0419 VP9 AFBC, **0425 H.265 AFBC (AFBC listed first; the 10-bit H.265 decoder still writes the 2-bit plane after the AFBC body)**, 0437 DDR mode, 0438 10-bit layout. Our `wt-vdec` series already has the equivalents, but our patch 27 deliberately makes 8-bit AFBC opt-in. The AFBC formats are reachable via S_FMT.
- **Kernel, display side (not in our tree; our `drivers/gpu/drm/sun4i/` has no `sun50i_afbc.c`):** LE 0244–0250 (`drm/gem` AFBC size checks, `sun4i` AFBC metadata, decompressor regs, VI-plane AFBC, "Enable AFBC on H616": "DE33 provides an AFBC decompressor on physical VI channel 0"), with format `DRM_FORMAT_YUV420_10BIT` → `SUN50I_AFBC_P010`. These sit on top of the DE33 rework 0201–0242 (register shadows, RCQ, shared DMA space). 10-bit HDMI: 0283–0285 (10-bit RGB / YUV 4:4:4 / prefer 10-bit YUV 4:2:2 at 4K50/60). Upstream-shaped copies are on `github.com/jernejsk/linux-1` branches `h616-de33-series-rewrite-v2` (faaea77e8a0a "Enable AFBC on H616", 41be334d0209 "Enable 10-bit YUV 4:2:0 output on H6 and H616", 2026-07-18/20) and `de3-afbc` (3ecaa72a0036).
- **FFmpeg:** LibreELEC master uses FFmpeg **9.0.2** + `packages/multimedia/ffmpeg/patches/v4l2-request/0001-v4l2-request.patch` (Kwiboo's v4l2-request series incl. Boris Brezillon's VP9 hwaccel. Patch 12/13 is Jernej's "hwcontext_v4l2request: Add support for AFBC_16X16_SPLIT pix fmts", 2025-12-14, mapping to `DRM_FORMAT_MOD_ARM_AFBC(16x16|SPARSE|SPLIT)`) + `0002-v4l2-request-vc1`, `0003-vc1-mpeg12-backports`. Alternatively `github.com/jernejsk/FFmpeg` branch `v4l2request-mpeg4`: our local copy `kernel-check/dl-vdec/ffmpeg-fork/hwcontext_v4l2request.c` l.88-106 has the same AFBC mapping.
- **Kodi:** LibreELEC master pins xbmc `e4b62810b1f3` = **Kodi 22.0 RC1** (Piers branch, 2026-10-22), DRM-PRIME/GBM.
- **Ready-made:** LibreELEC master `projects/Allwinner/devices/H616/README.md` lists `UBOOT_SYSTEM=orangepi-zero2` as a build target. The published H616 test images (https://jernej.libreelec.tv/images/h616/, 2026-09-30) cover only transpeed-8k618-t, x96-mate and x96q. https://jernej.libreelec.tv/test/h616-h618/ has an older (2024-02-17, LE 12) orangepi-zero2 image.

Ways to test (all need the user's go-ahead, since each runs or builds external code):
- **(a) Decode throughput only (no display):** build Jernej's FFmpeg fork (or LE's 9.0.2 + patches) on the board and run `ffmpeg -hwaccel v4l2request -hwaccel_output_format drm_prime -i hevc-main10-2160p60.mkv -f null -` with our kernel (AFBC10 is already the H.265 10-bit default in our series). Measure with `ve-busy.sh`. This answers whether AFBC10 decode reaches 60 on DDR3-1440. Bit-exactness cannot be checked by md5 (AFBC is compressed). Use a DE33 writeback or a GPU path later.
- **(b) End to end:** an LE `PROJECT=Allwinner DEVICE=H616 UBOOT_SYSTEM=orangepi-zero2` image (Kodi 22 + FFmpeg 9.0.2 + DE33 AFBC), or port LE 0201–0250 + 0283–0285 into our kernel and use `mpv --hwdec=drm --vo=drm`, or a minimal KMS client. Kodi's "dropped/skipped" counters (Shift+O) or DRM vblank timestamps give the 60 Hz verdict.

## 6. DRAM-type caveats

- H616-family DRAM differs per board: Zero2 (H616) DDR3, X96 Mate and Tanix TX6S DDR3 ([C] androidpctv), Zero3/Zero2W (H618) LPDDR4, Tanix TX1 LPDDR3 (Jernej, LE forum 2026-09-30: "The only other H616 family board with LPDDR3 is Tanix TX1"), RG35XX H (H700) DDR4 ([M] handtop PR).
- The vendor VE `ddr_mode` on H616 is fixed by IC version (DDR2_32 → field 2), **not** by DRAM type (§4), so no per-board VE setting is expected. Jernej's 256-bit fix was validated on boards that were not named.
- Peak bandwidth: DDR3-1440 x32 = 5.76 GB/s theoretical. LPDDR4 boards with a higher DRAM clock will have more headroom [I]. Jernej's 63 fps AFBC lower bound may come from an H618/LPDDR4 board, so **a Zero2 (DDR3) result could be lower**. That is a reason to measure (a) on our board rather than rely on his number.
- DE33 4K60 scanout of 10-bit AFBC (~17 MB/frame worst case, compressed less) plus VE traffic share the same DDR3. MBUS gives DE300 HIGHEST QoS, so under contention the VE slows first [I].

## 7. Recommended next experiments (in order; 1–3 are kernel debug knobs in our own driver with the existing GStreamer + `ve-busy.sh` harness, so they need no external code)

1. **Counters first (no code change, devmem only):** around one 600-frame 4K run each for tiled 8-bit, linear 8-bit and P010 10-bit, read (a) VE+0x20/0x24 DRAM read/write counters (enable bit 31; select bits VE_MODE 8/9), (b) IOMMU PMU for masters 2 and 3 (0x030F0200 enable, 0x230+0x10·m access/hit, 0x300+0x10·m latency), and (c) MBUS PMU 0x047fa09c / 0x047fa0ac (VE), 0x0c8 (VE1), 0x0d4 (total). Expected if §2 is right: similar write bytes, much lower IOMMU hit rate and/or higher read bytes for linear and P010. Caveat: the VE counters are reset by the VE reset that cedrus does between codec switches (our patch 29). VE_MODE is rewritten every job, so bits 8/9 must be added in `cedrus_engine_enable()` behind a debug param.
2. **P010 with a tiled hidden reconstruction:** a debug param that, for P010, programs `VE_PRIMARY_OUT_FMT_TILED_32_NV12` (then TILED_128 with 4 KiB-aligned planes) for the hidden recon instead of NV12, keeping `SECONDARY_EXT_NV12` + P010. Check md5 against the host (`board-10bit.sh`). Predicted ~40 fps HEVC Main10 if it works [I]. It may fail if the 2-bit plane or the secondary engine requires a linear primary; md5 will show that.
3. **IOMMU bypass A/B on 8-bit linear:** a debug param to set IOMMU_BYPASS bits 2 and 3 and allocate cedrus capture buffers contiguously from CMA (boot with cma=256M). Run 8-bit linear only, since 8 × 40 MB P010 won't fit. If linear jumps toward tiled speed, the TLB is the cause, and options open up (larger IOVA alignment, bypass for VE).
4. Cheap side knobs during 1–3: VE_MODE bit 20 `rec_wr_mode`; VE clock 624 MHz (after the VDD-SYS floor fix).
5. **AFBC10 decode throughput (needs user approval):** §5 (a). This is the definitive answer for the spec row. If ≥ 60 fps on Zero2 DDR3, follow with §5 (b) scanout (LE DE33 0201–0250, 0283–0285) for the end-to-end 4K60 claim.
